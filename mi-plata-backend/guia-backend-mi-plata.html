0. Antes de empezar: explicado desde cero

Una aplicación web tiene normalmente dos partes. La primera es el frontend: las pantallas, botones y formularios que ve una persona en el navegador. En Mi Plata está hecho en React. La segunda es el backend: el programa que decide si una operación es válida, guarda datos y responde al frontend. Este documento trata sobre esa segunda parte.

Piensa en un banco físico. La persona llega a una ventanilla con una solicitud; el cajero la recibe, revisa reglas, consulta los libros del banco y finalmente entrega una respuesta. El backend hace algo muy parecido:

¿Qué es una API?

API significa Application Programming Interface. Aquí es el conjunto de rutas que React puede llamar. Una ruta es como una dirección: POST /api/operaciones/retirar. POST dice que se enviarán datos para ejecutar una acción; la parte restante dice a qué operación se quiere llegar. React no entra a la base de datos: solo conoce estas rutas.

¿Qué es JSON?

JSON es un formato de texto para enviar datos. Usa llaves para un objeto, nombres de campos y valores. No es una tabla ni una clase Java; es el idioma de comunicación entre frontend y backend. Por ejemplo:

{
  "numeroCuenta": "AHO-001",
  "monto": 50000
}

Spring recibe ese texto y lo convierte a un objeto Java llamado MontoDTO. Luego, al responder, convierte otro objeto Java de nuevo a JSON. A este proceso se le llama serializar (objeto a JSON) y deserializar (JSON a objeto).

¿Qué es una base de datos?

MySQL guarda información de manera permanente en tablas. Una tabla se parece a una hoja de Excel: cada columna representa un dato y cada fila un registro. Por ejemplo, usuario tiene columnas como nombre, correo y clave; cada fila es un usuario. Java no manipula directamente las filas: JPA/Hibernate las representa mediante objetos como MUsuario.

¿Por qué no poner todo en una sola clase?

Se podría hacer un programa pequeño en el que una clase reciba HTTP, calcule y escriba SQL. Pero al crecer se vuelve difícil de entender, probar y cambiar. Si una regla de sobregiro cambia, habría que buscarla mezclada con rutas y consultas. Por eso Mi Plata separa responsabilidades: cada capa tiene una tarea clara. Esta es exactamente la lógica de arquitectura por capas que normalmente se enseña con el proyecto de concesionario.

1. Mapa general

Frontend React
   │ HTTP + JSON
   ▼

   ▼
Servicio (S...) ───── reglas del banco, validaciones y transacciones
   ▼
Repositorio (I...) ── consultas JPA / SQL sin escribir JDBC manualmente
   ▼
Modelo (M...) ────── mapeo objeto Java <─> tabla MySQL
   ▼
MySQL: mi_plata

Mapper / Projection ─── convierte o lee solamente los campos que se necesitan

La lógica sigue la separación del proyecto del profesor: el controlador no calcula saldos; delega en servicios. El servicio no abre conexiones SQL; usa repositorios. La entidad no es la respuesta pública directamente cuando hay un DTO más apropiado.

Convención de nombres: C significa controlador, S servicio, I interfaz/repositorio o mapper, y M modelo/entidad. Es una convención propia del proyecto, no una exigencia de Spring.

2. Cómo se conectan las capas

Ejemplo: una consignación

  1. React envía POST /api/operaciones/consignar con { numeroCuenta, monto }.
  2. COperaciones.consignar() recibe el JSON como MontoDTO.
  3. El controlador llama a SOperaciones.consignar().
  4. El servicio valida el monto con Dinero.validar(), busca y bloquea la cuenta a través de ICuenta, actualiza saldo y crea MMovimiento con tipo CONSIGNACION.
  5. @Transactional hace que saldo y movimiento se guarden juntos; si falla uno, se revierte todo.
  6. El servicio devuelve RespuestaOperacion; el controlador la manda como JSON y React muestra el mensaje.

Ejemplo: compra con tarjeta de crédito

COperaciones.comprar → SOperaciones.comprar valida tarjeta, límite y cuotas. Calcula la cuota con tasaMensual y numeroCuotas; el interés queda incorporado en la deuda de la compra, no como tipo de movimiento separado. Guarda MCompraTC, aumenta MTarjetaCredito.deudaActual y registra los movimientos COMPRA_TC y, si aplica, CUOTA_MANEJO.

Lectura detallada de una transferencia

Una transferencia es el mejor ejemplo para comprender por qué existen varias capas. Supón que Samuel envía $20.000 de AHO-001 a CTE-002.

  1. React crea un JSON de solicitud con cuenta origen, cuenta destino, monto y descripción.
  2. La petición llega a COperaciones.transferir(). El controlador no sabe cómo restar saldos: solamente recibe el DTO y delega en el servicio.
  3. SOperaciones.transferir() pide a ICuenta las dos cuentas. Las consulta bloqueadas para que dos operaciones simultáneas no gasten el mismo saldo por error.
  4. El servicio usa Dinero.validar(): el monto debe existir, ser numérico y mayor que cero. También comprueba que origen y destino no sean la misma cuenta y que ambas estén activas.
  5. Si la cuenta origen es de ahorro, no puede quedar negativa. Si es corriente, puede usar su limiteSobregiro hasta el límite permitido.
  6. El servicio resta $20.000 en la origen y suma $20.000 en la destino. Crea una fila MTransferencia y dos filas MMovimiento: TRANSFERENCIA_OUT y TRANSFERENCIA_IN.
  7. El repositorio guarda las entidades. Si cualquiera de esos guardados falla, @Transactional deshace lo anterior: no queda una cuenta descontada sin que la otra reciba el dinero.
  8. Finalmente, RespuestaOperacion vuelve al controlador y de ahí a React. React solo muestra el resultado; no decide el saldo.
Idea clave para sustentar: el movimiento no es el saldo. El saldo es el estado actual de la cuenta; el movimiento es el comprobante histórico que explica por qué el saldo llegó a ese valor.

Qué ocurre cuando se inicia la aplicación

  1. Java ejecuta MiplataApplication.main().
  2. SpringApplication.run(...) arranca Spring Boot y un servidor web integrado.
  3. @SpringBootApplication escanea el paquete base. Spring encuentra cada @RestController, @Service, @Repository y @Entity.
  4. Spring crea una sola instancia administrada —un bean— de los controladores, servicios y repositorios. Después conecta sus dependencias por inyección de dependencias.
  5. Spring Data JPA lee las entidades y configura Hibernate para hablar con MySQL usando los datos de application.properties.
  6. Como ddl-auto=none, Hibernate respeta la base existente: no crea ni cambia sus tablas. El archivo SQL es quien define el esquema.
  7. Cuando llega una petición, Spring localiza el método del controlador que corresponde a la ruta y verbo HTTP, y comienza el flujo mostrado arriba.

Cómo leer una clase del proyecto

Al abrir cualquier archivo Java, léelo en este orden:

  1. package: indica en qué carpeta lógica vive la clase, por ejemplo Servicio.
  2. import: lista otras clases que se necesitan. Que SOperaciones importe repositorios y modelos muestra que conecta reglas con persistencia.
  3. Anotación: antes de class, mira si dice @Service, @Entity o @RestController. Eso revela su papel.
  4. Atributos: son los datos que la clase conserva. En un servicio suelen ser repositorios inyectados; en una entidad son las columnas.
  5. Constructor: recibe dependencias. Spring lo usa para entregar repositorios al servicio y servicios al controlador. A esto se le llama inyección de dependencias.
  6. Métodos: tienen verbos: crear, buscar, transferir, eliminar. Revisa primero qué validan, luego qué consultan y finalmente qué guardan.
  7. return: indica el resultado. En servicios de operaciones suele ser RespuestaOperacion; en consultas, una lista o DTO.

Explicación más cercana de los DTO

DTO significa Data Transfer Object, u objeto para transportar datos. No contiene reglas grandes ni se guarda automáticamente en MySQL. Su función es evitar que el frontend mande o reciba toda una entidad.

  • LoginDTO contiene solo usuario y contraseña, porque es lo único necesario para iniciar sesión.
  • MontoDTO representa una operación sencilla sobre una cuenta: número de cuenta y monto.
  • TransferenciaSolicitudDTO agrega origen, destino, valor y descripción porque una transferencia necesita más datos que un retiro.
  • CompraSolicitudDTO agrega monto, cuotas, comercio/categoría para que la regla de TC pueda calcular la financiación.
  • PagoSolicitudDTO distingue tarjeta que se paga, cuenta desde la que sale el dinero y monto del abono.
  • RespuestaOperacion es el formato común de respuesta. En lugar de que cada controlador invente un JSON diferente, devuelve una bandera de éxito y un mensaje consistente.
  • ClienteBancoDTO y CuentaBancoDTO están pensados para la pantalla administrativa: organizan cliente y sus productos en una respuesta lista para consumir.

Modelo, tabla, clave primaria y clave foránea

Una entidad es una clase que representa una tabla. Por ejemplo, MUsuario representa usuario. Un objeto MUsuario representa una fila concreta. Su usuarioID es una clave primaria: un número único que identifica la fila.

Una clave foránea une tablas. La tabla cuenta contiene el identificador del usuario dueño; ese identificador apunta a una fila de usuario. Así se sabe a quién pertenece la cuenta sin repetir nombre, correo o contraseña en cada producto. Las anotaciones @JoinColumn, @ManyToOne y @OneToMany enseñan esa relación a JPA.

usuario (1) ──────── (N) cuenta (1) ──────── (N) movimiento
                         │
                         ├── (0..1) cuenta_ahorros
                         ├── (0..1) cuenta_corriente
                         └── (0..1) tarjeta_credito

cuenta (1) ─── (N) bolsillo / meta_ahorro / compra_tc

Por qué hay interfaces en repositorios

En Java, una interfaz define qué se puede hacer, no necesariamente cómo se programa por dentro. Por ejemplo, ICuenta declara que puede buscar y guardar cuentas. Al extender JpaRepository<MCuenta, Integer>, Spring Data crea la implementación automáticamente al arrancar. MCuenta indica el tipo de entidad; Integer indica el tipo de su identificador.

Una proyección es todavía más pequeña: una interfaz que declara únicamente getters para los campos necesarios en una consulta. Si el historial necesita fecha, tipo y valor, no hace falta cargar toda la cuenta y todas sus relaciones. Por eso existen IMovimientosUsuarioProjection, ICompraTCProjection e ITransferenciaProjection.

5. Anotaciones y palabras clave usadas

Precisión: Spring Boot no tiene “palabras reservadas” como Java. Lo que normalmente se llama así son anotaciones (empiezan con @), interfaces y convenciones. Aquí están todas las usadas por este backend y su conexión.
Anotación / términoQué hace aquí
@SpringBootApplicationCombina configuración, auto-configuración y escaneo de componentes. Está en MiplataApplication; permite que Spring encuentre controladores, servicios y repositorios.

@OneToMany(mappedBy="...")Una entidad reúne varias hijas. Ej.: un usuario tiene cuentas. mappedBy indica que la FK vive del otro lado.

Cómo se relacionan las anotaciones en una misma petición

@RestController + @RequestMapping("/api")
    └─ hace visible la clase COperaciones en la URL /api

@PostMapping("/operaciones/consignar") + @RequestBody MontoDTO
    └─ recibe POST /api/operaciones/consignar y transforma JSON a MontoDTO

@Service + @Transactional
    └─ SOperaciones ejecuta la regla y protege los cambios como una unidad

@Repository + JpaRepository + @Query
    └─ ICuenta / IMovimiento leen o guardan datos en MySQL

@Entity + @Table + @Column + @Id
    └─ MCuenta / MMovimiento indican cómo convertir objetos en filas

ResponseEntity<?> es un contenedor de la respuesta HTTP. Permite indicar cuerpo y código de estado. El ? significa “puede devolver distintos tipos de cuerpo”. En el proyecto se usa para que un mismo endpoint pueda devolver una respuesta correcta o un error controlado.

Palabras reservadas de Java que verás

6. Reglas de negocio que debes poder sustentar

  • Cuenta ahorro: no permite retirar más que el saldo disponible.
  • Cuenta corriente: permite bajar hasta -limiteSobregiro; ese atributo sí interviene en la validación.
  • Transferencia: descuenta origen y suma destino dentro de una transacción; quedan movimientos de salida y entrada, además del detalle de transferencia.
  • TC: no recibe consignaciones. Una compra aumenta deuda y un pago usa una cuenta origen para reducirla.
  • Interés TC: se calcula en código como parte de la financiación de la compra usando tasa mensual y número de cuotas; no existe una fila INTERES_TC en el catálogo de movimientos.
  • Bolsillo y meta: no crean dinero: mover al bolsillo/meta baja saldo de cuenta y aumenta el saldo interno; retirarlo hace el inverso.
  • Errores: los servicios lanzan ErrorNegocio o excepciones; los controladores responden con formato RespuestaOperacion y no deben filtrar detalles internos de MySQL.

8. Guion corto para sustentación

  1. “El frontend no toca MySQL; consume endpoints REST JSON.”
  2. “El controlador recibe HTTP, el servicio conserva las reglas y el repositorio persiste; así cada capa tiene una sola responsabilidad.”
  3. “Las entidades representan tablas; los DTO protegen y estabilizan el contrato que ve React.”
  4. “Las transacciones protegen operaciones monetarias: si no se puede guardar el movimiento, tampoco queda cambiado el saldo.”
  5. “La tarjeta calcula intereses dentro de la compra financiada. El interés no es un movimiento independiente.”
  6. “JPA une objetos y tablas mediante @Entity, relaciones y repositorios; Spring crea e inyecta los objetos con sus anotaciones.”
